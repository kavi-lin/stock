# 判斷力外化 — Rubric 與 Checklist

> 這份檔把「原本靠強模型直覺」的判斷寫成可查表的判準。拿不準時查這裡，不要靠感覺。
> 每條判準附正例（✅ 這樣做對）與反例（❌ 這樣做錯）。例子都取自本專案的真實情境。

## 1. 何時該升級模型

**判準**：任務含以下任一特徵 → 用當下最強檔（或 MODEL_DISPATCH.md §6 的多樣本評審）：
(a) 需要在互相矛盾的證據間裁決；(b) 沒有 schema 的自由生成且結果會進報告；(c) 需要跨 >3 個來源綜合出「原文沒寫的結論」；(d) 錯了會污染下游決策（buy/sell、position size）。

- ✅ 正例：sector Phase 4c Arbiter 要在 4 個 lane 提案 + Devil's Advocate 之間裁決 → 判斷密集（特徵 a+c+d），保留最強檔或 2+1 評審制。
- ❌ 反例：「把 30 個 SKILL.md 的 frontmatter 加一個欄位」用 opus 跑 → 這是機械任務（能寫出精確 before/after），haiku 就夠；用大模型是浪費不是謹慎。

**判準（升級時機）**：照 MODEL_DISPATCH.md §5 的階梯，關鍵是「帶軌跡」。
- ✅ 正例：sonnet 兩次沒把 validator 修到 rc=0，升級 prompt 附上兩次的 diff、rc 輸出、validator 報錯行 → 強模型第一次就修對。
- ❌ 反例：只寫「sonnet 修不好，換你修」→ 強模型重走一遍同樣的死路，燒兩倍 token。

## 2. 何時算「真的完成」

**判準**：同時滿足三條才能說完成：
(1) 驗收條件逐條有證據（rc 輸出、grep 計數、read-back 結果——不是「我做了」而是「這是輸出」）；
(2) fresh-context 驗證跑過（自己驗自己不算）；
(3) 收尾義務清完（dev session：三處版本同步驗證命令通過 + SESSION_NOTES/TODO 更新；protocol run：validator rc=0）。

- ✅ 正例：改了 `compute_price_framework.py` → 跑 `test_compute_price_framework.py` 貼出 `rc=0`、26 asserts pass → 版本三處 bump → 驗證命令輸出三個相同版號 → 完成。
- ❌ 反例：「我已修改引擎並確認邏輯正確，測試應該會過」→ 沒有 rc 輸出 = 沒完成。「應該」「理論上」出現在完成宣告裡就是未完成。

**部分完成要照實說**：做完 6/8 項就寫「6/8，剩這兩項卡在 X」。宣稱全部完成但實際 6/8，比誠實的 6/8 嚴重十倍——後者使用者能接手，前者會埋雷。

## 3. 何時該停下來問使用者

**判準**：滿足任一 → 停手先問：
(a) 動作不可逆且影響使用者資產/紀錄（刪檔、改 `positions.json`、改 `weights.yaml`、force push）；
(b) 兩條既有規則打架且檔案裡沒有優先序；
(c) 要改「使用者手動校準」清單上的東西（`weights.yaml`、`config/llm_config.json` 預算、mega-cap 名單）；
(d) 發現的問題暗示使用者的前提錯了（例：使用者要優化 A，但 A 其實沒被任何地方呼叫）。

- ✅ 正例：發現 `CLAUDE拷貝.md` 是冗餘副本 → 標註「建議刪除」留給使用者，不代刪——它是使用者手動建立的檔案（特徵 a）。
- ❌ 反例：為了「該用哪個測試框架」停下來問 → repo 裡已有 golden-fixture 慣例，查得到的事不問；問了就是把自己的功課丟給使用者。

**不該問的**：可逆的、repo 內有慣例可循的、使用者已授權範圍內的。先做，總結時報告即可。

## 4. 什麼訊號代表方向錯了（該換路，不是加力重試）

**判準**：出現任一訊號 → 停止目前路線，退回上一個分岔點換方法：
(a) 同一個錯誤修了兩次還在，且第二次的修法只是第一次的加強版；
(b) 為了讓方案成立，需要的「特例處理」越來越多（3 個以上 if/workaround）；
(c) 發現自己在改「不該由這層改」的東西（例：為了讓探索層資料進報告而去改 investment_protocol 的 gate）；
(d) 驗收條件本身開始被你重新解釋（「其實 rc=2 也算過」）。

- ✅ 正例：修 validator 報錯，兩輪後發現是 schema 本身與輸出格式演進脫節 → 停止 patch 輸出，回頭對 schema 與 protocol 做一致性檢查——問題在上游。
- ❌ 反例：測試一直紅，於是把 assert 的期望值改成實際輸出讓它變綠 → 這是訊號 (d) 的典型：你沒有修 bug，你修掉了偵測器。

**換路的動作**：寫 3 行「原路線、卡點、新路線」再開工——防止換湯不換藥。

## 5. 品質底線怎麼驗（分產出類型）

| 產出 | 底線（全過才出手） | 驗法 |
|---|---|---|
| 程式碼改動 | 對應測試 rc=0；沒動到的測試也沒變紅 | `OPS_COMMANDS.md` §7 對照表 |
| Protocol 輸出（分析/產業掃描/新聞） | validator rc=0；數字全部來自 script 輸出（抽 3 個數字回溯到 JSON 來源） | validator + 抽查 |
| 報告/文件 | fresh-context read-back：新 agent 能只憑檔案回答「這檔要我做什麼」且答對 | read-back 提問法 |
| 投資判斷類（verdict、Red Team、Arbiter） | 有明確反方：kill condition ≥2 條且可觀測（「毛利率連兩季 <X%」可觀測；「競爭加劇」不可觀測）；結論引用的每個數字有來源欄位 | 第二意見或 2+1 評審 |
| 批次改檔 | 改動處計數 = 預期計數；抽 3 處 diff 目測；`grep` 舊 pattern 為 0 | 計數 + 抽查 |

- ✅ 正例（kill condition）：「NVDA 資料中心營收 QoQ 轉負、或 top-2 客戶 capex 指引下修 >15%」→ 可觀測、可證偽。
- ❌ 反例：「若基本面惡化則退出」→ 不可觀測，等於沒寫。Red Team 產出裡出現這種句子 = 未達底線，退回重寫。

## 6. 誠實條款 — 這套制度補不了的事

拆解、驗證、多樣本評審能補**執行品質**；以下兩類補不了，遇到就照寫的做：

1. **模糊題／品味判斷**（「這篇市場導讀寫得夠不夠洞察」「兩個都合規的架構哪個優雅」）：多樣本評審只能防最差，選不出最好。處理順序：升到當下最強檔 → 還不夠就外部第二意見（codex/gemini）→ 仍分不出高下就把兩個選項＋trade-off 表給使用者選，**明說「這題超出我的可靠判斷範圍」**。
2. **無法驗證的事實**（付費牆後的資料、未來事件）：標註「未驗證」＋來源等級，禁止用流暢的行文掩蓋不確定。報告裡「未驗證」三個字不是丟臉，是合約。
