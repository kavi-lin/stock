## Root Cause Hypotheses

### Hypothesis A：抽取層文本正則化脆弱，未優先讀取結構化日誌
- **對應 pattern**：Pattern A（News macro_delta null 回升至 29.5%、Deep-dive trades 未 join）。
- **推論**：
  1. Extractor 當前主要依賴對 Markdown 報告的正則表達式搜尋（如尋找 `Macro Δ`、`session_macro_delta`）。當 LLM 報告生成微調排版（例如增加空格、改變加粗標籤 `**` 位置、或使用不同的標題層級）時，正則匹配容易破裂，導致資訊靜默遺失。
  2. 專案在運行中早已生成權威的結構化日誌（`news/news_logs/<date>_digest.json` 與 `investment/invest_logs/history.json`），但 `build_event_index.py` 仍以 Markdown 報告作為主要抽取來源，將原本確定性的數字降級為模糊的字串匹配。
- **驗證所需資料**：比對 31 筆 null news-digest 對應的 JSON 檔案，確認其鍵名一致性（已確認 104 份 JSON 存在且包含 18 筆強訊號）。

### Hypothesis B：多頭環境下正分模糊區強制觀望，造成機會成本型 miss
- **對應 pattern**：Pattern B（CANCEL miss 率高達 52.4%，score 0-0.8 miss 率 47.2%）。
- **推論**：
  1. 系統設定 `final_score` 落在 `[-staged, +staged]`（即 `[-0.8, +0.8]`）時預設為 HOLD，若疊加 risk_flag 或 cap 則降為 CANCEL。
  2. 在整體市場處於牛市或 RISK_ON（占完整 deep-dive 的 51% 以上）且熱門板塊強勢推升時，許多優質標的得分雖未達強烈買入門檻（≥1.2），但在 0-0.8 分數帶仍具備顯著動能。強制判定觀望後，標的持續平穩上漲（平均 miss return 達 +16.29%，但平均 drawdown 僅 -5.77%），造成「防守過當、實質錯過」的偏誤。
- **驗證所需資料**：檢查 66 筆 CANCEL miss 標的的 drawdown 與 runup 分布，確認是否具備回撤小、上漲大的特徵（已由 Rec 9 數據確認）。

### Hypothesis C：缺乏點時間緩存，導致歷史防污染機制採取粗暴截斷
- **對應 pattern**：Pattern C（全書 206 筆 deep-dive 歸入 Unknown）。
- **推論**：
  1. `_sector_heat.py` 調用 `company_context.get_profile(ticker)` 與當日最新 theme 快照，這些快照會隨時間變更。當 indexer 重新掃描歷史決策時，若使用當前快照去填補 4 月的決策，會發生「用未來的分類污染歷史」的缺陷（TODO-032）。
  2. 開發者為防止此現象，在 `deep_dive_extractor.py:628` 直接硬編碼 `heat = None`，但由於缺乏「決策日當時的 heat 靜態快照存檔」（Point-in-Time cache），導致整條分析鏈條在防護污染的同時失去了所有產業維度的可觀測性。
- **驗證所需資料**：檢視 `investment/invest_logs/` 下是否存在歷史 phase0 或 profile 快照可供回填。

### Hypothesis D：探索層評估粒度為「整份報告」，與主題生命週期存在生態謬誤
- **對應 pattern**：Pattern D（Thematic Mature miss 率反而偏低，Warning miss 率略高）。
- **推論**：
  1. Thematic screener 的 verdict 是對整份報告推薦的所有標的或整體方向給予單一標籤（hit/miss/neutral），而非對個別 theme 獨立結算。
  2. Mature 主題通常是大型權值股（如 Microsoft、Nvidia、TSMC 等成熟龍頭），這類公司在 2026 年大盤上行期表現極為穩健；即使主題已進入 Mature 階段，其股價往往持續創高。若僅憑「生命週期理論」直覺認為 Mature 主題風險高而提議壓低權重，反而會錯失最穩定的大盤 beta。
- **驗證所需資料**：需要對 thematic screener 內部各 theme 與 ticker 進行單獨的 5 日報酬追蹤，而非僅用報告總體 verdict 衡量。

### Hypothesis E：索引生成器缺乏執行實例雜湊，造成同日批次 ID 碰撞
- **對應 pattern**：Pattern E（5 組 ID 碰撞，6 surplus rows）。
- **推論**：
  1. `build_event_index.py` 在為 theme-detector 與 thematic-screener 分配 `decision_id` 時，採用了 `f"{source}_{date}"` 格式。當系統在同一天因重跑、除錯或多排程觸發而產出多份記錄時，後續運行的記錄與前次記錄發生鍵名衝突。
  2. 由於缺乏檔案名稱雜湊或 execution timestamp 作為次級鍵，同一 ID 在 diff 工具中被視為同一個決策的演變，干擾了翻轉率的精確計算。
- **驗證所需資料**：檢查 5 組碰撞檔案的原始路徑，確認是否為同日不同時間產出的檔案。

## 4. 系統盲點

1. **歷史快取防護造成的觀測黑洞**：為了解決 TODO-032 的「歷史分類被今日快照污染」，採取了將 `heat` 設為 `None` 的硬截斷方案。雖然達到了防止污染的目的，卻使整個 `industry_rollup` 徹底失去鑑別力（206 筆進入 Unknown），導致策略評估無法依產業熱度進行交叉驗證。
2. **抽取層「字串匹配優先」的架構倒退**：系統內部各 skill 已具備完備的 JSON 日誌輸出規範，但在日曆檢討層卻仍依賴 Markdown 爬蟲抽取。文本微調導致 31 筆 news macro_delta 丟失，凸顯了「以報告文本取代資料日誌」的架構脆弱性。
3. **回顧性報告的 100% n/a 誤區**：`short-term-weekly`（15 筆）與 `postmortem`（5 筆）在 verdict 統計中呈現 100% 的 `n/a`。檢查程式碼證實，此兩類報告本質為 Retrospective（回顧總結）性質，並非事前預測，因此沒有未來的股價結算窗口，100% n/a 是符合設計的正常現象，不應視為缺失 verdict 規則的 bug。
4. **決策層產出率長期低迷**：W34 至 W40 期間，除 2026-10-01 產出一筆 HPE deep-dive 外，momentum-screen（自 05-24 停產）、theme-detector、earnings-analyzer 均無任何新 run。樣本凍結使得 `accumulating_data` 類型的 TODO 陷入無意義的週度等待。
5. **權威診斷欄位暴露的輸入瑕疵**：本週 `authority_diagnostics` 檢出 1 筆 `run_evidence_mismatch`（`NVDA_20261001T003605_0eab632f7a`，指出 V5.5 run evidence 中 Burry 引擎輸入非規範格式，缺少 score/veto 映射）以及 4 筆 2026-08-09 的 `missing_provenance`。此類執行層細節需納入常態監控。
